# S1 preregistration

Sprint S1, the routing benchmark (hub #302). This file is committed before any question is written and before any model
call, and each phase adds its section before the step it governs. P1 writes **Inputs**: the composition first, in the
commit before any inventory is rebuilt, then the inventories' hashes and sources in its last commit. P2 appends the
questions' hashes; P3 writes the rest before G2. A run's files go under `benchmark/runs/<date>/`, and this file names them.

## Configurations (P3)

N is the inventory's size: 50, 200 or 1,000 (design §2.4). Every configuration builds every prompt and tool through the
router (`@typedstandards/civic-typed-router` 0.6.0, from this workspace) over the inventory's manifest
(`benchmark/inventories/to-manifest.mjs`), as the website's in-loop routing calls it (`benchmark/runner/session.mjs`);
the benchmark's own tools and texts are in `benchmark/runner/texts.mjs`, quoted below. No source is ever called: a row
ends at the model's tool call after its loads. In `baseline-7` Boston OpenContext is unconfigured, as production
configures it; in every other configuration every entry is configured, and the directory is the row's selection over
them. Every inventory entry outside the seven is offered with `requirement: required` by the loader (the router's
configuration reader knows only the seven's variables). The code is in `benchmark/runner/`, run by
`benchmark/runner/run.mjs` over the plan `benchmark/runner/plans/s1.json`.

| Configuration | The first request's directory | Tools on a selection request | Requests a row may send |
|---|---|---|---|
| `baseline-7` | the six configured of the seven | `load_source` | 2: the selection request, and the request after a load |
| `flat-50`, `flat-200`, `flat-1000` | every entry | `load_source` | 2 |
| `shortlist-N` | the place filter's shortlist, at most 25 | `load_source` | 2 |
| `shortlist+search-N` | the same shortlist, widened by each search | `load_source`, `find_source` | 4: up to three selection requests, then the request after a load |
| `builder-N` (main rows) | the builder's selection, at most 25 | `load_source` | 2 |
| `builder-N` (builder rows) | the full N-entry directory, read by Haiku 5.5 | `select_sources` | 1 |
| `rule-N` | none: no model | none | 0 |

**A row.** The selection request carries the directory as its system prompt and the question. When the response loads
at least one listed source, the request after it is the app's: the system prompt recomposed by the router over the
loaded sources, the app's load-result text for each load (`benchmark/runner/app-texts.mjs`; a load of an MCP Registry
entry returns the fixed text quoted under Inputs), `load_source` and the loaded sources' tools (with `find_source` in a
search row). A row's first loads are the loads of the response that first loaded something; in a search row that may
be the second or third selection request.

### `shortlist-N`: the place filter

The rule `place-filter`, version 1, cap 25 (`benchmark/runner/shortlist.mjs`), a pure function of the question's text
and the inventory:

1. **The gazetteer.** Each entry's names are its `place.names` and, for an entry with a `catalog`, its `displayName`.
   For a portal pack those are the catalogs' `owner_name` and `name` fields: P1's place-name rule derived `place.names`
   from them (the first is `owner_name` as given) and `displayName` is the catalog's `name` as given (both hold on every
   catalog pack of the 1,000-entry file). A name is kept only when one of its tokens is not a stop word: R5's BM25
   stopwords, P1's generic words, and the institution words below.
2. **Tokens.** A text is normalized (NFKD, combining marks removed), lower-cased and split on anything not a letter or
   a digit.
3. **A match.** A name matches when its tokens occur in the question's tokens as a contiguous run.
4. **The shortlist,** cut at the first 25: (a) every entry whose `place.level` is `multiple` or `international`, in the
   inventory's order; then (b) every other entry with a matching name, the longer longest match first (in tokens, then
   characters), ties in the inventory's order.
5. **No place, or an ambiguous one.** A question that names no place gets (a) alone. A name that fits several places
   matches every entry that carries it; the filter does not choose. An entry whose place is `unstated` (an MCP Registry
   entry) is never listed by the filter; `find_source` can reach it.

The directory lists the kept entries in the inventory's (manifest) order, as the router lists any selection. P1's
generic words, copied from `benchmark/inventories/rules.mjs`:

```text
open data opendata portal portals catalog catalogue hub site the of and for performance dashboard dashboards datos abiertos dados abertos donnees données ouvertes geoportal gis repository library platform official public government city town village county state commonwealth borough township parish municipality district province region national portale de del la le les di der die das satu dati aperti offene daten
```

The institution words, written from the gazetteer's one- and two-word names (the inventories, not the questions):

```text
department office agency bureau authority commission division administration ministry council board health local international network provincial regional school schools university college community financial finance treasury transport transportation transit police justice development humanitarian internet neighborhood spatial centre center publications metadata information services service statistics statistical ckan socrata datasets dataset catalogo plataforma portail ville comune generalitat capitol cohesion aids
```

**How it was written.** The rule was written after the questions were frozen, by an author who had read them. It reads
no label, and filter recall was not computed before the run, so the rule was not tuned against the gold. On these 149
questions no shortlist reaches 25 lines (the largest is 18, at 1,000), so the cap does not bind in this run: S1 measures
the filter, not the cap.

### `shortlist+search-N`: `find_source`, and the simulation of design §1.5

The search is BM25, method `bm25` version 1 (`benchmark/runner/search.mjs`): R5's rule chooser's parameters, declared
before R5's questions existed (k1 1.2, b 0.75, IDF ln(1 + (N − df + 0.5) / (df + 0.5)); each entry's document its alias
split on `_`, its display name and its description; R5's tokenizer and stopwords), returning the entries scoring above
0, best first, ties in the inventory's order, the first 10. It searches the whole inventory: in the benchmark every
entry is configured and none is Off, so the space is configured ∩ not-Off (design §1.5, step 1).

**The simulation.** After a search, the next request's directory text and `load_source` enum are rebuilt through the
router (`directoryPrompt`, `aliasedLoadSourceTool`) over the shortlist and every hit so far, in manifest order, so a
found entry takes its inventory position among the shortlist's lines (design §1.5, steps 1 and 2). No app does this yet
(S3 builds it); the runner simulates it so that the notice rate and recall after search can be measured first. The
cap applies to the shortlist, not to found entries.

**The limits.** A row sends at most three selection requests and one request after a load. A selection request is
sent first, and again after a selection response that called `find_source` and loaded nothing, while fewer than three
have been sent. At most two `find_source` calls a row are run; every call past the second is answered with the limit
text. A `find_source` call in the same response as a load is run, and its hits join the request after the load.

The tool, word for word:

```json
{
  "type": "function",
  "function": {
    "name": "find_source",
    "description": "Search every source this assistant can load, including sources the directory does not list, by what they hold and where. Returns up to 10 sources, best match first, and adds them to the directory and to load_source's choices for your next turn. Use it when no source in the directory fits the question.",
    "parameters": {
      "type": "object",
      "properties": {
        "query": {
          "type": "string",
          "description": "The records the question needs and the place they are for, in a few words."
        }
      },
      "required": [
        "query"
      ],
      "additionalProperties": false
    }
  }
}
```

What a call returns, word for word. A search with hits (shown for two hits and for one; the aliases are the hits, best
first):

> Found 2 sources, best match first: `nyc_charter`, `data_ny_gov`. Each is now listed in the directory in the system prompt, and load_source accepts its alias on your next turn.

> Found 1 source, best match first: `nyc_charter`. Each is now listed in the directory in the system prompt, and load_source accepts its alias on your next turn.

A search with no hit:

> No source matched that search. The directory is unchanged.

A call past the second:

> The search limit for this question is reached: find_source runs at most twice. Load a source from the directory, or answer without one.

### `builder-N`: the builder

Haiku 5.5 at low (its request parameters below) reads the question and the N-entry directory once per question, not
per repeat, and its selection is the shortlist of both main models' rows for that question; no search. A builder call
is a row of its own (role `builder`). Its system prompt, word for word:

> You choose which sources an assistant will see before it answers a question about public records. The assistant can load only the sources you choose, and it sees at most 25. The user message holds the question, then a line of three dashes, then the directory of every source, written for that assistant (it tells the assistant to load sources; you do not load anything). Call select_sources once with the aliases of the sources that could hold the records the question needs, best first, at most 25. Choose none when the question needs no data source. Do not answer the question.

Its user message is the question, a blank line, `---`, a blank line, and the router's directory over every entry of
the inventory (`builderUserMessage` in `benchmark/runner/texts.mjs`). Its one tool, word for word:

```json
{
  "type": "function",
  "function": {
    "name": "select_sources",
    "description": "Choose the sources the assistant will see: at most 25 aliases from the directory, best first. An empty list means the question needs no source.",
    "parameters": {
      "type": "object",
      "properties": {
        "aliases": {
          "type": "array",
          "items": {
            "type": "string"
          },
          "maxItems": 25,
          "description": "Aliases exactly as the directory writes them, best first."
        }
      },
      "required": [
        "aliases"
      ],
      "additionalProperties": false
    }
  }
}
```

The output rule, word for word:

> The selection is the `aliases` argument of the response's first `select_sources` call, read in order: an alias of the inventory is kept the first time it appears and ignored after; any value that is not an alias of the inventory is dropped and recorded; the first 25 kept are the selection. A response with no `select_sources` call, or whose arguments do not parse to an object with an `aliases` array, gives an empty selection, recorded as such. A main row whose selection is empty sends no request: nothing is offered, so nothing can be loaded, and the row is complete with no load.

A builder row that is an error leaves its question's main rows not started, recorded with the reason.

### `rule-N`, and `flat-1000`

- **`max_tokens`:** none of the open-weight models lists `max_completion_tokens`, which the catalog's rule would pick

- **The routing** keeps every open-weight request on an endpoint listing at most $0.15 per million input tokens and
  $0.60 per million output tokens (G0-3b's ceilings) and supporting every field sent. OpenRouter's headline price is its

- **The reasoning setting** is the effort Haiku runs at, `low`, where the model lists efforts. A model's reasoning tokens
  are completion tokens under its limit, and every bound counts the completion at that limit.
- **The reservation price** of a request is the most any endpoint it may land on lists, at the tier its estimate
  reaches: for Haiku every endpoint of its list (some list 10% above the headline, and $0.55 / $2.75 per million above
  100,000 prompt tokens); for an open-weight model its endpoints within the routing's ceilings, and the ceilings.
- **The roster check** (`benchmark/runner/roster.mjs`), before any spend: every model on OpenRouter's list, tools and
  every field sent listed as supported, the reasoning effort among the model's efforts, and some endpoint up, within the
  routing's prices and listing tools, `tool_choice` and every field sent.

**What was read.** OpenRouter's public model list and the five models' endpoints lists, with no key, on 2026-11-03


- per model, the calibrated characters per token: the fewest characters of a request body's JSON per billed prompt
  token over the two-question probe's requests, less 10%;
- per model, the largest billed completion: the most completion tokens one request billed (`completion_tokens`, which
  carries reasoning tokens; the reasoning tokens where reported larger), over the two-question probe's rows, the
  open-weight probe's rows of its winner, and for Haiku 5.5 R5's committed rows; and twice it, the completion
  allowance;
- the open-weight winner, each source read (run id and the sha256 of its rows), and what each figure was read from.

prints the calibrated bound before the evaluations:

## Repeats, cap, run order and fallback (P3)

As G0-3a was ruled. One invocation runs the evaluations in the plan's order, into one run directory with one
`meta.json`, one `rows.jsonl` and one contact ledger, every row tagged by its step:

```sh
node benchmark/runner/run.mjs --plan benchmark/runner/plans/s1.json --open-weight <slug> \
  --calibration <file> --cap <usd> [--option B]
```

1. `rule-50`, `rule-200`, `rule-1000` (no model, no spend);
2. `baseline-7`; `flat-50`; `flat-200`; `shortlist-50`, `-200`, `-1000`; `shortlist+search-50`, `-200`, `-1000`;
   `builder-50` (its reads, then its main rows); `builder-200` (the same): both main models, 149 questions, three

- **The open-weight slug** is a run argument fixed at G3 and recorded in `meta.json`, so the plan file does not change
  after G2.
- **The cap, and "the calibrated bound"** (the seat's ruling, hub #302 comment 6617296646). "The calibrated bound" is
  the plan's dry run recomputed at G3 with:
  1. each model's calibrated characters per token, from the two-question probe, as preregistered;
  2. each completion at twice the largest billed completion (reasoning included) measured for that model, over the probes' rows and, for Haiku, R5's committed rows;
  3. the open-weight winner at the price ceiling the run's provider routing enforces for it, not at its cheapest listed endpoint.

  Unchanged, and binding:
  - `--cap` is set at G3 from that bound, rounded up, and never above $100: the owner's G0-3a limit, with $70 the target.
  - Up to $100 the run keeps option A; above it, option B. No fallback beyond B is ruled: if B's calibrated bound also passes $100, the run does not start, and the seat brings it to the owner.
  - Every row still reserves its full worst case, so recorded spend plus the reservations in flight never pass `--cap`. A cap stop loses only the run order's last steps and is reported as such.

  As the runner computes it (`benchmark/runner/run.mjs`, `calibratedBound`): the plan's dry-run ceiling
  (`benchmark/runner/plan.mjs`: the first request as sent; the request after a load carrying the larger of the
  question's largest label and the directory's largest single source; in a search row two searches of ten hits), with
  each request's prompt at the model's calibrated characters per token, each
  completion and each earlier response a later request carries at the model's completion allowance (twice its largest
  billed completion) in place of the 4,000-token limit, the open-weight winner priced at its routing's ceilings ($0.15
  input and $0.60 output a million) and Haiku 5.5 at its dearest endpoint, at the tier the 25% margin gives; summed
  over the evaluations' steps at option A's repeats and at option B's. The dry run with `--calibration` and
  `--open-weight` prints both, then the option that applies and its `--cap` (the bound rounded up to a whole dollar), or
  that the run does not start. **Option B** (`--option B`) is two repeats on every configuration with three; the
  builder reads, the rule steps and the `flat-1000` probe unchanged.
- **Spend accounting** (A3.2; `benchmark/runner/engine.mjs`, `bounds.mjs`). Before a row's first request the runner
  reserves the worst case of every request its configuration allows (the table above), each priced at its reservation
  price with the estimate at the calibrated characters per token (2 until the probe), any request within 25% of a price
  tier's threshold at that tier, and its completion at the full limit, not the calibrated bound's allowance. A later
  request's prompt bound is its directory at its largest (every entry of it loaded; in a search row widened by the 20
  entries with the longest lines or the largest loaded state), each earlier response at its full limit with its tool calls answered (a tool call taken to
  cost at least 8 completion tokens), and never more than the model's context length. A row starts only if the spend
  so far, the reservations in flight and its own fit under the cap. Each request's slot is released as it returns and
  its cost charged: the larger of the cost at the listed price and the cost OpenRouter reported; a call that returns no
  usage is charged its worst case. So the spend recorded plus the worst cases in flight never passes the cap.
- **A row** is complete, error, or not started; never cut by the cap. An error row is a row a request of which failed
  after its attempts (three for no status, 408, 429 or 5xx; one otherwise): started and finished. On a cap stop the
  runner starts no other row, lets the rows in flight finish, records `stopReason` and the rows not started in
  `meta.json`, writes what it has and exits 2.
- **Where a run writes:** `benchmark/_local/runs/<run-id>/` (ignored); P4 copies the finished run into
  `benchmark/runs/<date>/`.
- **The inputs' hash** (A3.1): `node benchmark/runner/input-hash.mjs` prints the SHA-256 of the lines `<sha256>  <path>`
  (`sha256sum`'s) of every file under `benchmark/runner/` and `benchmark/scoring/` and every
  `benchmark/inventories/*.json` and `benchmark/questions/*.json`, sorted by path, byte order. The runner records it in
  `meta.json` at the run's start; the sprint's wrapper (G0-7) checks it before and after the run.

## Metric definitions (P3)

Design §2.5, as `benchmark/scoring/` computes them (`s1.mjs` per step and model; `metrics.mjs`; `offered.mjs`):

- **Raw gold and offered gold.** The raw gold is the question's `acceptable` for the row's inventory. The offered gold
  is the acceptable sets every alias of which was offered to the model in that row: its directory, plus every entry a
  search added (`row.offered`); when no set was wholly offered, it is `[[]]` (loading nothing is right). Every row is
  scored against both, and both are reported. So the seven questions whose gold at 7 is `boston` are scored under
  `baseline-7`, which does not list Boston, as questions with no offered source.
- **Recall@1st and recall@end**: R5's classes (`exact`, `acceptable` correct; `over`, `missing`, `wrong`) of the first
  loads and of the loads after the request that follows them, as rates over the rows. **Precision**: R5's `over` class,
  its rate.
- **The split is by gold, not by `kind`:** need-source (no empty set), no-source (every set empty) and open (an empty
  set beside a non-empty one), each under the gold it is scored by.
- **Filter recall, search recall at 5 and 10, the notice rate**: `metrics.mjs`, as its header defines them over the
  row fields `shortlist` (the first request's directory) and `searches` (each `find_source` call's query and hits).
  Search recall for `rule-N` is over its one search per question.
- **The error class**: per step and model, the error rows; an error row is in no recall or precision denominator, and
  `uniqueRows = completeRows + errorRows` over the rows started.
- **The pick counts** (the seat's notes): per step and model, the rows whose first loads were correct on the offered
  gold and held a synthetic copy; the rows whose first pick was an MCP Registry entry; the rows whose first pick was a
  CKAN pack.
- **Tokens, latency, cost, consistency**: first-request prompt tokens (median, min, max), prompt and completion tokens
  per row and completion tokens per request (medians), the directory's share of the first request's characters, and
  reasoning tokens; first and second request latency (median, p90); the charged cost, in all and per row; the share of
  questions whose repeats loaded the same set. The unnoticed-miss rate is not measured (S2).
- **The builder rows**: errors, empty selections, dropped aliases and the filter recall of the selection. **The
  summary** (`node benchmark/scoring/analyze.mjs <run dir> --out <file>`) names the three run files' SHA-256 and holds
  no clock and no path, so the same files give the same bytes.
